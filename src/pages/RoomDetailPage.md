# RoomDetailPage

Room detail page rendered at `/pokoje/:roomId`, reached by tapping a room row in [HomePage](HomePage.md)'s "Pomieszczenia" list. Follows the lofi "Room detail" mockup: a back arrow + room name header, a bordered stat box (spent / planned / budget + a [SpentPlannedBudgetBar](../components/SpentPlannedBudgetBar.md)), and two list sections ("Zaplanowane pozycje" and "Faktury").

## Data

Subscribes live (`onValue`) to `settings/rooms/:roomId` (same path/shape as [RoomsSection](../components/RoomsSection.md) and [RoomFormPage](RoomFormPage.md)) to read the room's `name` and `budget`.

Also subscribes live (`onValue`) to the flat `planItems` path (see [PlanItemFormPage](PlanItemFormPage.md)) and filters client-side for items whose `roomId` matches this room — the RTDB has no per-room subcollection, so filtering happens in JS after the full `planItems` snapshot arrives. Filtered items are then sorted by `order` (missing `order` treated as `0`). It also subscribes to `settings/shops` to resolve each item's `shopId` to a shop name. The "Zaplanowane pozycje" list is rendered via [SortableList](../components/SortableList.md) — dragging a row to reorder it writes the new `order` value for every plan item in this room back to `planItems/<id>/order` in one multi-path `update()`, and local state is updated optimistically. Each item shows: name; the item's `tags` (if any) as a wrapped row of small Chakra `Tag` badges directly under the name (each clickable to toggle it into/out of the page's tag filter — highlighted `solid`/`primary` when active, `subtle`/`gray` otherwise); `price × amount` formatted as currency (`+ szt.` suffix when amount > 1); shop name with a `ShoppingBasket` icon (when `shopId` is set); delivery cost/days with `Trolley`/`Hourglass` icons and a `·` separator (when `pickupType` is `delivery` and either is set); and target date with a `Calendar` icon plus a human-readable relative offset in parentheses (e.g. "za 2 miesiące") computed by the local `formatRelativeTarget` helper via `Intl.RelativeTimeFormat('pl-PL')` (when `targetDate` is set). Each row is wrapped in [SwipeableRow](../components/SwipeableRow.md): its always-visible action column only holds a `Link`-icon button (only when `link` is set) that opens the item's link in a new tab, while a `FileText` action (only when `notes` is set, opens a Chakra `Dialog` modal showing the item's name and notes) and a `Pencil` action (navigates to `/pozycje/:itemId`) are revealed by swiping the row left. `planned` is the sum of `price × amount` across all of this room's items (unaffected by the tag filter). "+ Pozycja planu" links to `/dodaj?roomId=...` to preselect this room in the add form; [PlanItemFormPage](PlanItemFormPage.md) assigns new items `order = max(existing in this room) + 1` so they land at the end.

Clicking any item's tag toggles it into local `activeTags` state (AND-filtered — an item must have every active tag to stay visible). While `activeTags` is non-empty: the active tags are echoed as removable Chakra `Tag`s (click, or the tag's own close trigger, un-toggles it) in a `Wrap` row under the "Zaplanowane (N)" heading — the count in that heading reflects the filtered list, not the room total; the row switches from the drag-sortable `SortableList` to a plain (non-draggable) list, since reordering only the filtered subset would corrupt the `order` field for hidden siblings; and an empty-filter-result state ("Brak pozycji z wybranymi tagami.") is shown separately from the "no plan items at all" empty state. Tag filtering and reordering are mutually exclusive by design — clear the filter (or click a tag again) to drag-reorder.

### Bulk tag selection

Swiping a plan item row right (via [SwipeableRow](../components/SwipeableRow.md)'s `onSwipeRight`) toggles that item's id into local `selectedItemIds` state; selected rows get `SwipeableRow`'s `selected` visual (tinted background + left border) via `selectedItemIds.includes(item.id)`. This selection is independent of `activeTags` filtering/reordering and only applies to plan items, not invoices. While `selectedItemIds` is non-empty, a floating action bar (`position: fixed`, pinned above the bottom tab bar at a hardcoded `bottom="84px"` matching the tab bar's approximate rendered height) shows the selection count and four `IconButton`s:

- **Dodaj fakturę** (`FilePlus` icon) — navigates straight to `/faktury/nowa?roomId=...&itemIds=id1,id2,...` (no modal), preselecting both the room and the selected plan items as linked items on [InvoiceFormPage](InvoiceFormPage.md)'s add form. Selection state is left as-is (the page unmounts on navigation anyway).
- **Dodaj tag** (`Tag` icon) — opens a Dialog with a Chakra `TagsInput` (same free-typed multi-tag pattern as [PlanItemFormPage](PlanItemFormPage.md), minus its existing-tag autocomplete dropdown); confirming merges the entered tags into every selected item's `tags` array (deduped per item) via one multi-path `update()`, then clears the selection.
- **Usuń tagi** (`CircleMinus` icon, disabled when the selection has no tags at all) — opens a Dialog listing the union of tags present across selected items as clickable Chakra `Tag`s (`solid` when picked for removal, `subtle` otherwise, same toggle pattern as the tag-filter chips above); confirming removes the picked tags from every selected item's `tags` array via one multi-path `update()`, then clears the selection.
- **Odznacz wszystko** (`Xmark` icon) — clears `selectedItemIds` without touching Firebase.

Both tag dialogs' "confirm" buttons are disabled until at least one tag is entered/picked; canceling (or the dialog's own close trigger) discards the in-progress modal state without touching selection or Firebase.

Also subscribes live (`onValue`) to the flat `invoices` path (see [InvoiceFormPage](InvoiceFormPage.md)) and filters client-side for invoices whose `roomId` matches this room, then sorts by `order` (missing `order` treated as `0`). `spent` is the sum of each invoice's `realCost` plus, when its `pickupType` is `delivery`, its `deliveryCost`. `budget` still reads from the room's `budget` field. The "Faktury" section is also rendered via [SortableList](../components/SortableList.md) — dragging to reorder writes the new `order` for every invoice in this room back to `invoices/<id>/order` in one multi-path `update()`. Each row shows `title` (falling back to "Faktura" if empty), total cost, date with a `Calendar` icon, a `Receipt` icon, and, per row, a `FileText` icon button when `notes` is set plus a pencil edit link to `/faktury/:invoiceId`; "+ Dodaj fakturę" links to `/faktury/nowa?roomId=...` to preselect this room in the add form, and [InvoiceFormPage](InvoiceFormPage.md) assigns new invoices `order = max(existing in this room) + 1`. An invoice has no shop field of its own — instead, each row resolves shop/supplier names by looking up the invoice's `linkedItemIds` against the already-loaded `planItems` list, reading each linked item's `shopId`, resolving those against `shops`, deduping, and rendering the (possibly multiple) names with a `ShoppingBasket` icon, same as the plan-item rows above — only shown when at least one linked item has a shop. The notes `Dialog` is shared between plan items and invoices via a generic `{ title, notes }` `notesEntry` state (rather than one keyed to `PlanItem` specifically).

## Props

None (reads `roomId` from the route via `useParams`).

## Use cases

- Drilling into a single room from the home page to see its budget breakdown.
